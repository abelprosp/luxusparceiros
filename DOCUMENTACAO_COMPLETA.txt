1. APRESENTAÇÃO
===============

Luxus Parceiros é uma plataforma de gestão da operação comercial da Luxus
Telefonia. O sistema centraliza o relacionamento entre a administração da
plataforma, empresas parceiras, matrizes, filiais e usuários operacionais.

O projeto possui:

- sistema web responsivo;
- API própria;
- aplicativo móvel;
- banco de dados PostgreSQL;
- autenticação e permissões;
- notificações em tempo real;
- armazenamento protegido de documentos;
- ambiente Docker;
- configuração de produção para Railway.

O sistema é multiempresa. Cada empresa parceira trabalha dentro do seu próprio
espaço e não pode visualizar dados de empresas concorrentes.


2. OBJETIVO DO SISTEMA
======================

O sistema permite administrar:

- parceiros comerciais;
- matriz e filiais;
- usuários e acessos;
- operadoras e planos;
- linhas e chips;
- estoque e movimentações;
- clientes;
- vendas e portabilidades;
- documentos das vendas;
- campanhas e metas;
- comissões;
- registros financeiros;
- solicitações operacionais;
- chamados de atendimento;
- notificações;
- auditoria;
- indicadores e relatórios.

O modelo hierárquico é:

Administrador da plataforma
  └── Parceiro comercial (matriz)
        ├── Filial 1
        ├── Filial 2
        ├── Filial N
        └── Usuários vinculados ao parceiro ou a uma filial

O administrador global pode acompanhar todo o ecossistema. Um parceiro enxerga
somente sua própria empresa e suas filiais. Um usuário de filial fica limitado
à loja em que está vinculado.


3. ARQUITETURA E ORGANIZAÇÃO DO PROJETO
=======================================

O repositório é um monorepo gerenciado com pnpm workspaces.

Estrutura principal:

luxusparceiros/
  apps/
    api/                 API NestJS
    web/                 Sistema web Next.js
    mobile/              Aplicativo Expo/React Native
  packages/
    types/               Tipos, enumerações e permissões compartilhadas
    utils/               Funções utilitárias compartilhadas
    ui/                  Componentes compartilháveis
  docker/
    api.Dockerfile       Imagem de produção da API
    web.Dockerfile       Imagem de produção do site
    api-entrypoint.sh    Migrações e inicialização da API
    nginx.conf           Proxy local
  docs/                  Documentação complementar
  uploads/               Arquivos locais em desenvolvimento
  docker-compose.yml     Ambiente local completo
  railway.toml           Configuração Railway da API
  railway.web.toml       Configuração Railway do site
  .env.example           Exemplo de variáveis
  README.md              Apresentação técnica resumida
  pnpm-workspace.yaml    Definição do monorepo
  package.json           Comandos gerais

Arquitetura de produção:

Navegador ou aplicativo
  ├── HTTPS → Next.js (web)
  ├── HTTPS → NestJS (API)
  └── WebSocket → Socket.IO

API NestJS
  ├── Prisma → PostgreSQL
  ├── Redis
  └── Volume persistente → /app/uploads

No desenvolvimento local, o NGINX expõe tudo em http://localhost e encaminha:

- / para o serviço web;
- /api para a API;
- /socket.io para a comunicação em tempo real.

5. PERFIS, PERMISSÕES E HIERARQUIA
==================================

5.1 ADMIN
---------

Possui todas as permissões.

Existem dois comportamentos:

- ADMIN sem partnerId: administrador global da plataforma;
- ADMIN com partnerId: administrador limitado ao parceiro vinculado.

O vínculo comercial sempre prevalece. Um ADMIN vinculado a um parceiro não pode
usar o papel administrativo para consultar concorrentes.

5.2 SUPERVISOR
--------------

Perfil de gestão operacional. Pode visualizar parceiros e filiais, trabalhar
com clientes, vendas, estoque, chamados, solicitações, usuários, campanhas e
dashboard conforme as permissões definidas.

Não recebe automaticamente todas as permissões destrutivas ou financeiras.

5.3 PARTNER
-----------

Representa o responsável pelo parceiro comercial/matriz.

Pode:

- visualizar e administrar suas filiais;
- cadastrar clientes e vendas;
- consultar operadoras e planos disponíveis;
- consultar linhas e estoque do seu escopo;
- acompanhar comissões;
- usar chamados e solicitações;
- visualizar seu dashboard.

Não pode consultar outro parceiro.

5.4 ATTENDANT
-------------

Usuário de filial.

Pode operar clientes, vendas, estoque, chamados, solicitações e dashboard, mas
fica limitado à filial vinculada no login.

Na criação de venda, a filial responsável já vem preenchida e não pode ser
trocada por outra loja.

5.5 FINANCIAL
-------------

Perfil voltado a:

- consulta e gestão de comissões;
- aprovação de comissões;
- registros financeiros;
- chamados relacionados;
- dashboard compatível com seu escopo.

5.6 Permissões granulares
-------------------------

As permissões seguem o formato modulo:acao, por exemplo:

- partners:read, partners:write, partners:delete;
- branches:read, branches:write, branches:delete;
- clients:read, clients:write, clients:delete;
- sales:read, sales:write, sales:delete;
- plans:read, plans:write;
- stock:read, stock:write;
- commissions:read, commissions:write, commissions:approve;
- tickets:read, tickets:write;
- requests:read, requests:write;
- users:read, users:write;
- financial:read, financial:write;
- campaigns:read, campaigns:write;
- audit:read;
- dashboard:read.

As definições ficam em packages/types/src/index.ts.


6. ISOLAMENTO ENTRE EMPRESAS E FILIAIS
======================================

O isolamento é feito na API e não depende apenas de esconder opções na tela.

Regras:

1. Usuário com partnerId sempre usa o parceiro do próprio login.
2. Se tentar enviar o ID de outro parceiro, a API rejeita o acesso.
3. Usuário ATTENDANT deve possuir branchId.
4. Usuário de filial consulta somente sua filial.
5. Administrador global é ADMIN ou SUPERVISOR sem partnerId.
6. Dados de vendas, clientes, documentos, dashboard e relatórios respeitam o
   mesmo escopo.
7. Exportações não ampliam a permissão do usuário.

Comportamento das filiais:

- parceiro matriz vê somente suas próprias filiais;
- parceiro não vê lojas concorrentes;
- atendente vê somente sua loja;
- filial escolhida em uma venda deve pertencer ao parceiro da venda;
- qualquer tentativa de acesso direto por URL também é validada pela API.

Helpers principais:

- apps/api/src/common/utils/partner-scope.ts
- apps/api/src/common/utils/branch-scope.ts

8. FLUXOS DE NEGÓCIO IMPORTANTES
================================

8.1 Cadastro de parceiro
------------------------

1. Administrador global abre Parceiros.
2. Cadastra dados da empresa.
3. Pode cadastrar o primeiro usuário.
4. Define ou associa planos.
5. O parceiro passa a acessar somente o próprio ambiente.
6. O parceiro pode criar suas filiais.

8.2 Cadastro de filial
----------------------

1. Parceiro abre Filiais.
2. Informa dados da loja, login e senha.
3. O backend confirma que o parceiro pode administrar a filial.
4. Cria a filial.
5. Cria um usuário ATTENDANT vinculado à filial.
6. A filial herda planos e operadoras do parceiro.

8.3 Criação de plano
--------------------

Plano específico:

1. Administrador cria o plano.
2. Informa partnerId.
3. O sistema cria um vínculo PartnerPlan.
4. Matriz e todas as filiais desse parceiro passam a utilizá-lo.

Plano global:

1. Administrador cria sem partnerId.
2. O sistema vincula o plano aos parceiros ativos.
3. Parceiros elegíveis passam a visualizá-lo.

8.4 Nova venda
--------------

1. Selecionar parceiro quando o usuário for global.
2. Selecionar matriz ou filial responsável.
3. Selecionar operadora e plano permitido.
4. Informar linha, chip e ICCID.
5. Informar formato do contrato.
6. Opcionalmente marcar contrato assinado e anexá-lo.
7. Informar cliente.
8. Anexar CPF, RG e foto do chip.
9. Informar portabilidade quando aplicável.
10. Registrar a venda.
11. A venda entra em análise.

8.5 Aprovação da venda
----------------------

1. Administrador/supervisor analisa a venda.
2. Confere os dados e documentos.
3. Se faltar documento, solicita ao parceiro.
4. Parceiro reenvia os arquivos solicitados.
5. Para aprovar, o contrato assinado deve existir.
6. Todos os documentos obrigatórios devem estar cumpridos.
7. Ao aprovar, o sistema registra data e processa a comissão.
8. A venda pode depois ser ativada ou cancelada conforme a transição permitida.

8.6 Correção de venda
---------------------

1. Abrir Vendas.
2. Abrir o menu de ações.
3. Selecionar Editar venda.
4. Corrigir os campos permitidos.
5. Anexar o contrato quando pendente.
6. Salvar.
7. A API revalida escopo, telefone, plano e filial.

8.7 Documento perdido
----------------------

1. O registro continua aparecendo na venda.
2. A interface detecta que o arquivo físico não está disponível.
3. Exibe Reanexar arquivo.
4. O usuário autorizado escolhe novamente o documento.
5. O sistema preserva o registro e grava o novo arquivo.

Esse recurso não recupera automaticamente arquivos antigos apagados do
armazenamento. É necessário possuir a cópia original.

---------

- IN_ANALYSIS: em análise;
- APPROVED: aprovada;
- PENDING: pendente;
- REJECTED: rejeitada;
- ACTIVATED: ativada;
- CANCELLED: cancelada;
- CONTESTED: contestada;
- DOCUMENTS_PENDING: documentos pendentes.

Transições principais:

- Em análise → aprovada, rejeitada, pendente, contestada ou docs pendentes.
- Pendente → em análise, aprovada, rejeitada, contestada ou docs pendentes.
- Docs pendentes → em análise, aprovada, rejeitada ou contestada.
- Contestada → em análise, aprovada, rejeitada ou docs pendentes.
- Aprovada → ativada ou cancelada.
- Ativada → cancelada.
- Rejeitada e cancelada são situações finais no fluxo atual.

17. ARQUIVOS, DOCUMENTOS E VOLUME PERSISTENTE
=============================================

Desenvolvimento local:

- arquivos ficam em ./uploads ou no volume uploads_data do Docker.

Railway:

- arquivos devem ficar no volume montado em /app/uploads;
- o filesystem comum do contêiner é temporário;
- um novo deploy pode substituir o contêiner;
- sem volume, arquivos enviados podem desaparecer.

Importante:

- PostgreSQL guarda o registro e o endereço do documento;
- o volume guarda os bytes reais do arquivo;
- backup do banco não substitui backup dos uploads;
- backup dos uploads não substitui backup do banco;
- os dois devem ser protegidos.

Arquivos antigos perdidos:

- não podem ser recriados a partir do nome;
- precisam ser anexados novamente;
- a função Reanexar arquivo resolve o vínculo quando existe a cópia original.

23. SOLUÇÃO DE PROBLEMAS
========================

23.1 Docker não conecta
-----------------------

Sintoma:

failed to connect to docker API

Verificar:

1. Docker Desktop está aberto?
2. O status mostra Engine running?
3. Contêineres Linux estão habilitados?
4. WSL/Virtual Machine Platform estão disponíveis?
5. docker version responde com Client e Server?

Comandos:

docker version
docker compose ps

23.2 Railway falha no healthcheck
---------------------------------

API:

- config file deve ser railway.toml;
- healthcheck /api/health;
- DATABASE_URL válida;
- PORT fornecida pela Railway;
- migrations sem erro;
- volume com permissão de escrita.

Web:

- config file deve ser railway.web.toml;
- healthcheck /login;
- NEXT_PUBLIC_API_URL correta durante o build;
- API e CORS corretos.

23.3 Site abre, mas API falha
-----------------------------

- conferir NEXT_PUBLIC_API_URL;
- não colocar /api duas vezes;
- conferir CORS_ORIGINS;
- conferir HTTPS;
- abrir /api/health;
- olhar logs da API.

23.4 Documento não aparece
--------------------------

- conferir volume na API;
- mount path /app/uploads;
- conferir se o arquivo existe;
- conferir autenticação;
- usar Reanexar arquivo quando o original foi perdido.

23.5 Parceiro vê dados errados
------------------------------

- conferir partnerId do usuário;
- conferir branchId do atendente;
- conferir perfil;
- renovar o login após mudar vínculos;
- testar a API diretamente;
- revisar uso dos helpers de escopo.

23.6 Plano não aparece para filial
----------------------------------

- conferir vínculo PartnerPlan;
- conferir se isActive está true;
- conferir situação do plano;
- conferir operadora;
- conferir partnerId do login;
- lembrar que o plano pertence ao parceiro, não à filial.

23.7 Venda não aprova
---------------------

- conferir contrato assinado;
- conferir foto do chip;
- conferir CPF e RG;
- conferir documentos adicionais solicitados;
- conferir situação atual;
- conferir se o usuário pode aprovar;
- abrir Editar venda para anexar contrato pendente.

23.8 Venda rejeitada não aparece no dashboard
---------------------------------------------

Esse é o comportamento correto:

- a venda rejeitada aparece em Vendas;
- não é venda realizada;
- não entra nos indicadores.


24. DECISÕES FUNCIONAIS CONHECIDAS
==================================

1. Matriz e filiais compartilham planos e operadoras.
2. Planos são vinculados ao parceiro, não copiados para cada filial.
3. Parceiro vê todas as suas filiais.
4. Atendente vê somente sua filial.
5. Parceiros não veem concorrentes.
6. Contrato é opcional no cadastro e obrigatório na aprovação.
7. Marcar contrato assinado exige arquivo real.
8. Venda rejeitada continua disponível para consulta.
9. Somente APPROVED e ACTIVATED contam como venda realizada.
10. Chamados e solicitações continuam separados até definição do fluxo.
11. Documentos são protegidos e dependem de armazenamento persistente.
12. Exportações respeitam o mesmo isolamento da tela.

27. INTEGRAÇÃO COM O LUXUS TASK
===============================

Objetivo:
  permitir que uma demanda seja aberta no Luxus Parceiros e trabalhada
  normalmente dentro do Luxus Task.

O Luxus Task continua independente:
  usuários do próprio Task continuam criando, editando e concluindo demandas
  pelo fluxo já existente. A integração é apenas uma entrada adicional.

Fluxo:

1. O usuário abre Demandas no Luxus Parceiros.
2. Informa tipo, descrição, cliente opcional e responsável do Luxus Task.
3. A API do Parceiros cria um registro local e envia a demanda ao Task.
4. O Task cria ou reutiliza o usuário técnico inativo LUXUSPARCEIROS.
5. A nova demanda aparece no Task como criada por LUXUSPARCEIROS.
6. O responsável trabalha nela normalmente no Task.
7. Alterações e conclusão geram callback para a API do Parceiros.
8. O Parceiros atualiza status, resolução, responsável e protocolo externo.
9. Ao abrir o detalhe, também é feita reconciliação por consulta, protegendo
   contra callbacks temporariamente perdidos.

Chamados e solicitações:
  o menu principal passa a possuir somente Demandas como entrada para novos
  atendimentos. Chamados antigos permanecem acessíveis pelo botão
  "Chamados anteriores", sem perda ou migração destrutiva de histórico.

Segurança:
  a comunicação usa x-integration-key e comparação em tempo constante.
  A chave existe somente nas APIs e nunca é enviada ao navegador ou aplicativo.
  O parceiro e a filial são obtidos da sessão autenticada no backend.

Variáveis no serviço API do Luxus Parceiros:

  LUXUS_TASK_API_URL
  LUXUS_TASK_INTEGRATION_KEY

Variáveis no backend C# do Luxus Task:

  LUXUS_PARCEIROS_INTEGRATION_KEY
  LUXUS_PARCEIROS_CALLBACK_URL
  LUXUS_PARCEIROS_TECHNICAL_USER_EMAIL

LUXUS_TASK_INTEGRATION_KEY e LUXUS_PARCEIROS_INTEGRATION_KEY precisam conter
exatamente o mesmo segredo forte.

Migrações obrigatórias:

  Luxus Parceiros:
    apps/api/prisma/migrations/20260728120000_luxus_task_integration/migration.sql

  Luxus Task/Supabase:
    supabase/migrations/20260728_luxus_parceiros_integration.sql

Endpoints no Luxus Task:

  GET  /integrations/luxus-parceiros/responsaveis
  POST /integrations/luxus-parceiros/demandas
  GET  /integrations/luxus-parceiros/demandas/{requestId}

Endpoint de retorno no Luxus Parceiros:

  POST /api/integrations/luxus-task/callback

Falhas:
  se o Task estiver indisponível, a demanda local não é apagada e mostra o erro
  de sincronização. O usuário pode usar "Tentar sincronizar novamente".
  O Task não perde uma conclusão caso o callback falhe, pois o Parceiros
  reconcilia os dados ao consultar o detalhe.


28. PRIVACIDADE DO RANKING
==========================

O ranking usa somente vendas realizadas: APPROVED ou ACTIVATED.

Administrador:
  pode ver o ranking geral e os detalhes globais permitidos pela função.

Parceiro e filial:
  veem somente a própria posição no ranking. Qualquer abertura de detalhes,
  relatório ou exportação usa partnerId e branchId derivados da autenticação.
  Um partnerId enviado pelo navegador não substitui o escopo autenticado.
  Nenhum cliente, documento, valor ou venda de concorrente é retornado.
