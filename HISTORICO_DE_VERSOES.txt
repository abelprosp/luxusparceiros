HISTÓRICO DE VERSÕES — LUXUS PARCEIROS
======================================

Atualizado em: 19/10/2026
Versão atual: 1.12.0
Repositório: https://github.com/abelprosp/luxusparceiros (branch main)
Sistema web: https://parceiros.grupoluxus.com.br

Este arquivo registra cada versão do sistema e cada troca feita: qual era o
problema, por que foi resolvido daquele jeito e o que foi usado. Os códigos
entre colchetes (ex.: [0b16b67]) são os commits no GitHub; com eles dá para
abrir a mudança exata com "git show <código>".

A numeração de versões foi organizada a partir do histórico do Git. A
DOCUMENTACAO_COMPLETA.txt marca a versão 1.0.0 em 28/07/2026, data da
integração com o Luxus Task; as versões anteriores aparecem como 0.x.


TECNOLOGIAS USADAS NO PROJETO (VISÃO GERAL)
-------------------------------------------

- Monorepo com pnpm workspaces e Turborepo (apps/api, apps/web, apps/mobile,
  packages/types, packages/utils, packages/ui).
- API: NestJS (TypeScript), Prisma ORM 6 com PostgreSQL, class-validator nos
  DTOs, JWT para login, Socket.IO para avisos em tempo real, Swagger.
- Web: Next.js 14 (React), Tailwind CSS, componentes no estilo shadcn/ui
  (Radix), lucide-react nos ícones, Leaflet no mapa de parceiros.
- Planilhas: write-excel-file (gera .xlsx) e read-excel-file (lê .xlsx).
- Mobile: Expo / React Native.
- Publicação: Docker (api.Dockerfile, web.Dockerfile, Nginx) na Railway, com
  deploy automático a cada push na main. As migrações do banco rodam no
  início do container (docker/api-entrypoint.sh: prisma migrate deploy).
- Testes da API: node:test sobre o código compilado (apps/api/test).
- Integrações: Luxus Task (demandas), telefonia-2 / sistema de faturamento
  da Luxus (vendas concluídas cobradas pela Luxus), API externa de consulta.

0.1.0 — 30/06 a 07/07/2026 — Base do sistema e primeiro deploy
==============================================================================

1) Código inicial do monorepo [86cbaca, a48af7a]
   Problema: não existia sistema para os parceiros da Luxus registrarem
   vendas, clientes, estoque, comissões e chamados.
   Por quê: centralizar a operação comercial dos parceiros em um só lugar,
   com cada empresa vendo só o que é dela.
   O que foi usado: API NestJS + Prisma/PostgreSQL, painel Next.js, app
   Expo, pacotes compartilhados de tipos e utilitários, Docker e Railway.
   Módulos criados: autenticação, usuários, parceiros, filiais, clientes,
   operadoras, planos, linhas, chips (SIM cards), estoque, vendas,
   comissões, financeiro, campanhas, solicitações, chamados, notificações,
   auditoria e dashboard.

2) Correções do primeiro deploy na Railway [7915f57, bb407bb, 82b349a,
   e092b29, 841bfd0, 7dd34d2]
   Problema: o deploy falhava. O .gitignore escondia a pasta do módulo de
   uploads; o container baixava o Prisma 7 (incompatível); a API não passava
   no healthcheck; faltavam dependências no container final.
   Por quê: sem isso a API não subia em produção.
   O que foi usado: ajuste do .gitignore, build de @luxus/types e
   @luxus/utils antes da API e da Web, Prisma 6 fixado, entrypoint próprio
   (docker/api-entrypoint.sh), "pnpm deploy" para empacotar node_modules,
   PORT explícito, railway.toml e railway.web.toml, .dockerignore.

3) Rota raiz e dados iniciais [6436a17, d09481b, d5691b3, 114c161, e8651a4]
   Problema: abrir a URL da API dava 404 sem explicação; o banco novo vinha
   vazio.
   Por quê: facilitar o diagnóstico e ter operadoras, planos, filiais e
   chips de exemplo para começar.
   O que foi usado: root.controller.ts com resposta informativa; seed do
   Prisma (prisma/seed.ts) executado no entrypoint.

0.2.0 — 07/07/2026 — Portal do parceiro, filiais, notificações e visual
==============================================================================

1) Web alinhada ao app para o perfil parceiro [79a17ea]
   Problema: o parceiro via menus e ações de administrador.
   Por quê: cada perfil deve ver só a sua operação.
   O que foi usado: controle de acesso por perfil (lib/rbac.ts), telas de
   clientes, filiais e perfil, dashboard próprio do parceiro. O seed deixou
   de rodar a cada deploy para não recriar dados.

2) Ajustes de parceiros, estoque, linhas, planos e vendas [358f3c9,
   8672cac, 495fead, 8bf9d61, 7ce01e9, d09ea2b]
   Problema: filtro de status de parceiros e campanhas quebrava; estoque
   não carregava; faltavam reenvio de documentos e planos por parceiro.
   O que foi usado: DTOs de consulta com validação, novas rotas de estoque e
   linhas, vínculo parceiro x plano, tela de reenvio de documentos da venda,
   página "Esqueci minha senha".

3) Login de usuários de filial e notificações [06709e5]
   Problema: filiais não tinham login próprio e não havia avisos no sistema.
   Por quê: a filial precisa trabalhar isolada, e todos precisam saber quando
   algo muda.
   O que foi usado: migração branch_user_login, escopo por filial
   (common/utils/branch-scope.ts), sino de notificações com Socket.IO, tela
   de detalhe da venda.

4) Identidade visual e layout no celular [7ee9c9a, 0b3c4cf, 1c945b4,
   49058ea, 14ec222, 6479262]
   O que foi feito: logos claro/escuro, nova tela de login, mapa de parceiros
   (Leaflet), menu lateral e menu móvel, cartões de lista para celular,
   edição de chamados, página de configurações.

   reanexar documentos perdidos.

1.2.0 — 04 a 07/08/2026 — Aprovação de vendas pelo Luxus Task e contratos
==============================================================================

1) Venda aprovada vai ao Luxus Task (#24, #25, #28) [8aaa318, 382bccd,
   1616b54, aa60261]
   Problema: aprovar a venda não gerava nada no Luxus Task e a venda não era

   Problema: anexos do Task não chegavam ao Parceiros e vice-versa.
   O que foi usado: callback recebendo os anexos e envio dos novos uploads à
   demanda integrada; notificação a quem abriu a venda.

4) Vários acessos com o mesmo CNPJ [cbc32b9, 939fb39]
   Problema: um mesmo CNPJ não podia ter mais de um parceiro cadastrado.
   O que foi usado: remoção da unicidade do documento e aviso na tela;
   ajuste do seed.

1.4.0 — 17 a 27/08/2026 — API externa, prazos e Task assumindo a demanda

   do Nginx configurável.

   Problema: era possível trocar a vez de uma venda já concluída.

   Por quê: sistemas de terceiros precisavam consultar vendas sem acessar o

   O que foi usado: módulo external-sales protegido por chave de API.

4) Resolver no Parceiros sem depender do Task [62d88de, 806ef79, dcd2ed4]
   O que foi feito: finalizar venda travada no Task, reabrir venda concluída
   e mostrar quem está na vez.

5) Sincronização confiável com o Task [dc356b0, 48d10ab, d668da9, 5880c6e,
   0b1a95d]
   Problema: sync falhava por protocolo duplicado, marcava sucesso sem
   enviar RG/CPF e não mandava todos os dados da venda.
   O que foi usado: recuperação do vínculo da demanda, sync que só marca
   sucesso com todos os arquivos, limite do corpo em 50 MB, assunto e
   observações com linha, endereço e telefone, botão Sincronizar que espera
   o resultado e rota GET /sales/:id com o resumo para o Task.

6) Prazos [c663149, 324b6db, fac9eb7, aea2ac5]
   Problema: era possível aprovar com prazo no passado, e o prazo chegava ao
   Task com um dia a menos.
   Por quê: o fuso horário convertia o fim do dia para UTC e mudava a data.
   O que foi usado: validação na API e no formulário (sugestão de +7 dias),
   edição do prazo e envio como data pura (aaaa-mm-dd).

7) Fluxo simplificado: o Task assume a demanda [a5fb268, c864e2f, 51f4ceb,
   69045f7, 0eec543, 81814bf]
   Problema: o vai-e-volta de "vez" entre os sistemas confundia.
   Por quê: o Luxus Task passa a conduzir tudo depois do envio e o Parceiros
   só espelha.
   O que foi usado: remoção da troca de vez e do contrato em branco,
   conclusão automática pelo callback, resumo do Task na venda, avisos em
   tempo real que podem ser marcados como lidos.

1.10.0 — 14/10/2026 — Envio ao sistema de faturamento da Luxus (telefonia-2)
==============================================================================

1) Vendas concluídas vão ao telefonia-2 [0348c68, 77987f3]
   Problema: as vendas concluídas precisavam entrar no sistema de faturamento
   da Luxus (Luxus Connect / telefonia-2). A primeira rota usada dava 404.
   Por quê: o operador do telefonia-2 publicou a porta de entrada
   /api/v1/intake/customers, autenticada pelo cabeçalho X-API-Key.
   O que foi usado: módulo telefonia-intake na API, com fila e nova
   tentativa; o envio não desfaz a conclusão da venda. O pacote enviado segue
   as regras do telefonia-2: telefone de 10 a 15 dígitos, ICCID de 19 a 22,
   IMEI de 15, EID de 32, anexos PDF/JPEG/PNG/WebP de até 8 MB cada (16 MB
   no total, máximo 10). Telefone ou e-mail inválido vai nas observações em
   vez de bloquear. A mesma venda reenviada não duplica (o telefonia-2
   responde "replayed"). Configuração na Railway: TELEFONIA_INTAKE_URL e a
   chave do operador.

2) Escolha da cobrança em cada venda [77987f3]
   Problema: nem toda venda é cobrada pela Luxus; as que não são não devem
   ir ao faturamento.
   O que foi usado: campo billedByLuxus na venda (migração
   20261014170000_sale_billed_by_luxus, padrão "sim"). Vendas novas são
   obrigadas a escolher no cadastro; as antigas e as em andamento ficaram
   como "cobrança pela Luxus". Só vendas com cobrança pela Luxus entram na
   fila do telefonia-2. As vendas já concluídas foram enviadas.

3) Texto da escolha [fb32503]
   Problema: o texto citava "telefonia-2", nome interno que o usuário não
   entende.
   O que foi feito: "A cobrança será feita pela Luxus — esta venda vai para
   o sistema de faturamento da Luxus" e "A cobrança não será feita pela
   Luxus — esta venda não vai para o sistema de faturamento da Luxus".

1.12.0 — 19/10/2026 — Importação de vendas por planilha, guia e histórico
==============================================================================

1) Importação em massa por planilha Excel
   Problema: cadastrar muitas vendas uma a uma era lento, e havia vendas já
   concluídas no Luxus Task que ainda não estavam no Parceiros.
   Por quê: permitir que o parceiro ou o administrador baixe uma planilha
   padrão, preencha as vendas e envie tudo de uma vez.
   Como funciona:
   - Em Vendas, botão "Importar". Escolhe-se o tipo:
     a) "Vendas novas (vão para aprovação)": cada linha vira uma venda em
        "Aguardando análise". O administrador aprova e ela segue para o
        Luxus Task, como no cadastro normal. A planilha não leva fotos, então
        o administrador pode pedir os documentos na análise. Disponível para
        administrador, parceiro e filial.
     b) "Vendas já concluídas no Luxus Task" (só administrador): cada linha
        vira uma venda concluída, ligada ao protocolo do Task, com comissão e
        contando no dashboard pela data da venda. Nada é enviado nem alterado
        no Luxus Task. Se a cobrança for da Luxus, a venda segue para o
        sistema de faturamento.
   - "Baixar planilha" gera o arquivo .xlsx com as abas: Vendas (para
     preencher), Instruções (o que vai em cada coluna, se é obrigatória e
     um exemplo), Planos (operadora, plano e preço) e, para o administrador,
     Parceiros e lojas. Assim os nomes são escritos iguais ao cadastro.
   - Proteções: cada linha é validada sozinha e as linhas com erro não
     impedem as outras; o resultado mostra a linha e o motivo. Bloqueia
     linha vendida que já tem venda ativa, protocolo do Task já importado,
     linha ou protocolo repetido na mesma planilha, linha igual ao telefone
     de contato, datas impossíveis ou no futuro. Cliente com o mesmo CPF no
     mesmo parceiro é reaproveitado. Máximo de 300 vendas por arquivo.
   - Cuidados com o Excel: CPF digitado como número recupera o zero da
     frente; ICCID e EID digitados como número (o Excel corta depois de 15
     dígitos) são recusados com o pedido para formatar a coluna como Texto.
   O que foi usado:
   - Web: write-excel-file para gerar a planilha e read-excel-file (nova
     dependência) para ler o arquivo no navegador
     (apps/web/src/lib/sales-import.ts e
     apps/web/src/components/sales/sales-import-button.tsx).
   - API: rota POST /api/sales/import (permissão de criar vendas). A
     validação de cada linha fica em sales-import.parse.ts; a gravação em
     sales-import.service.ts. As vendas novas reaproveitam o mesmo cadastro
     da tela (SalesService.create), com as mesmas regras de eSIM,
     portabilidade, plano do parceiro e comissão. As concluídas seguem o
     modelo da cópia histórica (versão 1.9.0) e geram a comissão.
   - Testes: apps/api/test/sales-import.test.js.
